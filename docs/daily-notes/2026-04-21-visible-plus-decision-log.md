## 6. 为什么一直只有 2 条：用户页面和自动化页面不是同一个上下文

  - 用户看到的是“已经滚好并渲染出来”的活页面。
  - 但 CLI 后续命令每次都在重新开新上下文，导致抓不到同样的页面状态。

## 13. 慢网环境：phase1 批跑开始做稳定性工程
由于用户说明当前网络环境较差，且暂时还在做别的任务，所以后续明确要求：
- 继续开发
- 不做联网真实测试

在这个要求下，项目继续新增了多层“慢网友好能力”。

### 13.1 限额控制
为 `run-phase1-batch` 增加：
- `--video-limit-per-target`
- `--comment-video-limit-per-target`
- `--browser-timeout-ms`

目的：
- 控制每个主页最多拿多少条视频做 detail。
- 控制每个主页最多拿多少条视频做 comment。
- 对慢网临时拉长超时。

### 13.2 分批执行（chunked phase1）
继续新增：
- `--chunk-size`
- `--pause-seconds`
- `run_phase1_chunked(...)`

作用：
- 把一轮 20 个账号切成多个小批次。
- 每个 chunk 单独产出 artifact。
- chunk 之间可暂停几秒。

### 13.3 失败恢复
之后又继续给 chunked phase1 增加：
- `status`（每个 chunk 的 success / failed）
- `failed_chunks`
- `rerun_targets_count`
- `rerun_manifest_path`

作用：
- 如果后面某些 chunk 跑失败，可以直接把失败的 target 抽出来形成一个 rerun manifest，便于后续重跑。

### 13.4 运维观察
再往后继续增强：
- `duration_sec`
- `slowest_chunks`
- `rerun_command_example`

作用：
- 可以看到哪些 chunk 最慢。
- 可以生成推荐重跑命令。
- 周报 Markdown 也开始支持展示 chunk 失败摘要、慢 chunk TOP、推荐重跑命令。

# Part C：可公开决策过程说明

## 决策 1：为什么先从“数据收集”而不是“分析/话术”开始
因为用户一开始虽然同时提了：
- 数据抓取
- 画面/人物特征量化
- 视频话术并行处理
- 账号分析

但用户自己也明确指出：
- “分析和话术的前提不是抓取么”

所以项目一期优先级被明确成：
1. 主页 -> 视频列表
2. 视频详情 -> 互动指标
3. 评论 -> 正文与互动
4. 再把它们送入分析层

这就是为什么今天几乎所有后续推进，都围绕抓取链路打通展开。

## 决策 2：为什么没有在主页提取 2 条之后立刻扩大到 20 个账号
因为当时证据显示：
- `子琦` 主页页面上明明有“作品 593”
- 自动化却只能稳定拿 2 条

如果在这个阶段就去跑 20 个账号，只会把缺陷扩散到更多目标，得到大量质量很差的 artifact。  
因此先集中打一个典型主页，把提取路径打实，再扩到多账号，更符合最小闭环策略。

## 决策 3：为什么改成 CDP / 活窗口抓取
多轮实验证明：
- 用户眼前看到的页面，已经滚出来很多视频
- 但 CLI 每次新开页面上下文，都抓不到同样的渲染状态

这说明问题不是账号本身，也不是登录本身，而是：
- “已经渲染好的活页面状态”无法被新开页面复现

所以最有效的技术路线，就从“继续猜页面结构”改成了：
- 直接连接用户当前已经滚好的活浏览器页面
- 从同一个上下文抓 DOM / href / runtime

这是一个非常关键的路线转换，也是今天最大的突破之一。

## 决策 4：为什么先只做 10 条真实样本，而不是 50 条全部拉完
虽然通过 CDP 已经抓到了 50 条视频，但一上来全量做 detail/comment 会有几个问题：
- 网络慢，时间成本太高
- 评论提取当时还是 placeholder
- 详情页真实指标还没稳定
- 盲目扩大样本会让调试成本变高

所以先选 10 条，是为了：
- 先验证详情页真实指标是否可提取
- 再验证评论正文是否可提取
- 再看分析是否有基本可用性

这符合“先打一条窄而完整的链路”的原则。

## 决策 5：为什么 `view_count` 先保守置 0
因为在多条视频里都出现了类似污染：
- 页面里账号头部的“获赞 32.2万”
- 很容易被误识别成视频的 `view_count / like_count / comment_count`

相较于错误地写入一个看起来像真值但其实是污染值的指标，更稳妥的做法是：
- 暂时把 `view_count` 保守处理为 0
- 先优先保证 `like/comment/share` 的质量

这样可以避免后面分析层被错误数据带偏。

## 决策 6：为什么要引入 meaningful 统计
在最初的 full-batch 里，“成功”更多表示：
- 跑了 detail
- 跑了 comments
- 但不一定真的提到有用数据

例如评论 placeholder 也可能被记成执行成功。  
这会让周报和账号评分看起来“采集成功率很高”，但其实没有真实业务价值。

因此引入 meaningful 的原因是：
- 把“执行成功”与“得到有效内容”分开
- 让分析层更诚实地反映当前质量
- 后续才更容易比较不同账号、不同 chunk 的真实价值

## 决策 7：为什么后面主要做“稳定性工程”，而不是继续追求更大样本
因为用户明确说了：
- 当前网络环境不好
- 还在处理别的任务
- 希望继续开发，但不做实际测试

在这个前提下，最合适的研发工作就不是“继续拼更多线上抓取”，而是：
- 给后续真实跑批先做好基础设施
- 提高容错性
- 降低卡死风险
- 增加可恢复能力

所以后半段开发重点自然转向：
- 限额
- chunk 分批
- pause
- rerun manifest
- rerun command
- slowest chunks

## 决策 8：为什么 chunked phase1 要做失败清单和推荐重跑命令
因为真实环境下，最容易出现的情况不是“完全失败”，而是：
- 一批里有些账号好，有些账号坏
- 某个 chunk 慢
- 某个 chunk 失败
- 某些 target 需要补跑

如果没有失败切片与推荐重跑命令，后续使用就会变得很笨重：
- 只能整轮重跑
- 很难知道该从哪继续
- 很难区分哪些结果还值得保留

因此这一层能力本质上是在把脚本式采集，往“可操作的批处理系统”方向推。

## 决策 9：为什么最后选择导出“可见完整记录 + 决策说明”版本
因为用户后面希望：
- 让别人看起来像翻今天聊天一样
- 同时也关心系统提示和隐藏推理

系统提示与隐藏推理不能直接导出，但真正的业务诉求是：
- 让别人读完后，既知道今天说了什么，也知道为什么这么做

因此最合适的替代方案就是：
- Part A：保留可见对话和可见推进记录
- Part C：补充可公开的决策过程说明

这样既满足了“像回看今天对话”的需求，也尽量接近“理解我们的思路”的目标。
